### Task 1: The SPA rewrite

The single change that makes share links work in production. Without it, `/letter/<slug>` reaches Vercel's static file server, matches no file, and 404s — and a direct hit is the only way anyone ever arrives at that URL.

**Files:**
- Create: `vercel.json`

**Interfaces:**
- Produces: every path served by `index.html`, so client-side routing resolves

- [ ] **Step 1: Write the config**

Create `vercel.json` at the repository root:

```json
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}
```

That is the whole file. Vercel checks the filesystem BEFORE applying rewrites, so `/robots.txt` and the hashed `/assets/*` files continue to serve normally — the catch-all does not swallow them. Do not add an `excludes` list or negative lookaheads to "protect" static files; they are already protected, and the extra pattern is a thing to get wrong.

- [ ] **Step 2: Confirm it is valid JSON and nothing else broke**

```bash
node -e "JSON.parse(require('fs').readFileSync('vercel.json','utf8')); console.log('valid json')"
npm run typecheck && npm test && npm run build && npm run lint
```
Expected: valid json, typecheck clean, 42 passing across 4 files, build succeeds, exactly two `set-state-in-effect` warnings.

- [ ] **Step 3: Confirm the file would actually be used**

Run: `ls vercel.json && git check-ignore vercel.json || echo "not ignored — will be committed"`
Expected: the file exists and is NOT gitignored. A `vercel.json` that never reaches the remote fixes nothing.

- [ ] **Step 4: Commit**

```bash
git add vercel.json
git commit -m "fix: serve index.html for every path so deep links resolve"
```

### Task 2: Code-split the public route

**Files:**
- Modify: `src/app/App.tsx`

**Interfaces:**
- Consumes: the existing `PublicLetter` default export
- Produces: `PublicLetter` in its own chunk, behind a Suspense boundary

WHY ONLY THIS ROUTE: the owner and their partner open this app and stay in it, so splitting their routes saves them a few kilobytes once and adds boundaries to get wrong. `/letter/:slug` is different — it is opened by strangers, on mobile, from a message, and they currently download the entire application (auth, compose, archive, both modals) to read one letter once. This is the one route where the download lands on someone who did not choose to be there.

- [ ] **Step 1: Replace the static import with a lazy one**

In `src/app/App.tsx`, add a new import line at the top. The file currently has
no `react` import — the react-router-dom and framer-motion lines stay exactly as
they are:

```tsx
import { lazy, Suspense } from 'react'
```

Remove this line:

```tsx
import PublicLetter from '../routes/PublicLetter'
```

and add, below the other imports:

```tsx
// Split so a stranger following a link from a message downloads the letter and
// little else, rather than the whole app — auth, compose, archive and both
// modals — to read one letter once. The signed-in routes stay eager: those two
// open the app and stay in it, so splitting them would buy nothing.
const PublicLetter = lazy(() => import('../routes/PublicLetter'))
```

- [ ] **Step 2: Wrap the route in Suspense**

Replace the public route line:

```tsx
            <Route path="/letter/:slug" element={<PublicLetter />} />
```

with:

```tsx
            <Route
              path="/letter/:slug"
              element={
                <Suspense
                  fallback={
                    <div className="flex min-h-screen items-center justify-center bg-paper-app">
                      <p className="font-ui text-sm text-ink-muted">One moment…</p>
                    </div>
                  }
                >
                  <PublicLetter />
                </Suspense>
              }
            />
```

The fallback deliberately matches `PublicLetter`'s own loading state exactly — same wrapper classes, same copy — so a stranger sees one continuous waiting state rather than a flash of one followed by another.

Leave the `/letter` and `*` NotFound routes as they are, and leave the comment above the public route in place.

- [ ] **Step 3: Verify the split actually happened**

```bash
npm run build
```

Expected: `dist/assets/` now contains a SEPARATE chunk for the public letter page alongside the main index chunk, and the main chunk is smaller than before. Before this task the build produced a single `index-*.js` of about 609 kB (about 179 kB gzipped).

Run: `ls -la dist/assets/*.js`
Report every JS file and its size. If there is still only ONE JS file, the split did not happen — say so rather than reporting success; a `lazy()` whose import is also statically imported elsewhere gets merged back into the main chunk.

- [ ] **Step 4: Verify nothing else moved**

```bash
npm run typecheck && npm test && npm run lint
```
Expected: typecheck clean, 42 passing across 4 files, exactly two `set-state-in-effect` warnings.

Start the dev server and fetch `/`, `/archive`, `/letter/anything` and `/nonsense`. All four must return HTTP 200. Then stop it.

- [ ] **Step 5: Commit**

```bash
git add src/app/App.tsx
git commit -m "perf: split the public letter route so strangers download less"
```

### Task 3: The deploy guide

**Files:**
- Create: `DEPLOY.md`

- [ ] **Step 1: Write the guide**

Create `DEPLOY.md` at the repository root:

```markdown
# Deploying Dear Jee

Hosted on Vercel at `dearjee.vercel.app`. Supabase is the backend; there is no
server-side application code.

## First-time setup

1. **Import the repository** into Vercel. The framework preset is Vite; the
   defaults (`npm run build`, output `dist`) are correct.

2. **Set the environment variables** — Project Settings → Environment
   Variables, for the Production environment:

       VITE_SUPABASE_URL=https://<your-project-ref>.supabase.co
       VITE_SUPABASE_ANON_KEY=<the anon / public key>

   Both come from Supabase → Settings → API Keys. The anon key is public by
   design: it identifies the project, and row-level security is what protects
   the data. The `service_role` key must never go here — it bypasses RLS
   entirely.

3. **Redeploy.** This step is not optional and not obvious.

## The two things that bite

**Vite inlines `VITE_`-prefixed variables at BUILD time.** They are baked into
the JavaScript bundle when Vercel builds it. Changing one in the dashboard
does nothing until you redeploy — there is no server process to restart.

**How to tell whether it worked:** if the environment variables are missing,
the app does not error. It silently falls back to the in-memory mock and shows
every visitor three seeded letters about someone waking before an alarm. If you
see those on the live site, the variables are not set, or you have not
redeployed since setting them.

**`vercel.json` must be present.** It rewrites every path to `index.html`.
Without it, `/letter/<slug>` and `/archive` return 404 — and a direct hit is
the only way anyone reaches a share link. This failure exists only in
production; the dev server handles it invisibly.

## In Supabase

- **Site URL** → the Vercel domain. No current flow depends on a redirect URL
  (password auth, email confirmation off), but leaving it as `localhost` is
  what breaks the first feature that does need it.
- **Close sign-ups** — Authentication → Sign In / Providers — but ONLY after
  both accounts exist. Closing them first locks out whoever has not registered
  yet, and the invite flow requires the second person to create an account
  before they can redeem a code. Check Authentication → Users and count the
  rows before flipping it.

## After deploying

Open a share link **on a phone, on a different network** — not a private window
on the same machine. That single action is the only thing that exercises the
rewrite, the build-time environment variables, the anon key, the
`get_public_letter` function and the RLS path together. Each has been verified
alone; the combination has not.
```

### Task 4: The structural responsive audit

This task produces a FINDINGS DOCUMENT, not fixes. Read the components, list what is suspect, change no styling.

**Files:**
- Create: `docs/superpowers/specs/2026-09-10-responsive-audit.md`

- [ ] **Step 1: Audit every component and route**

Read every file under `src/components/` and `src/routes/`. For each, record anything in these four categories, with a file:line reference:

1. **A width that cannot shrink below 375px.** `max-w-[600px]` and `max-w-[420px]` are FINE — `max-w` caps without forcing. A bare `w-[420px]` or a `min-w-` would not be. The known instances of `max-w-[…]` are in `ComposeLetter.tsx`, `LetterModal.tsx`, `ShareModal.tsx`, `AuthScreen.tsx`, `JoinPartner.tsx`, `SetupProfile.tsx` and `PublicLetter.tsx` — confirm each is `max-w` and not something stricter.
2. **Horizontal overflow risk.** Long unbroken strings are the danger. Both `ShareModal.tsx` and `InviteLink.tsx` render a full share URL; check each has `break-all` or an equivalent. Also check the letter body, which renders arbitrary user text with `whitespace-pre-wrap`.
3. **Tap targets under 44px.** The small text buttons at the bottom of `LetterModal` (Archive, Delete, and the two-step confirm), the close and share icon buttons, and the header links. Report the rendered size implied by the padding classes.
4. **Anything positioned absolutely** that could collide on a narrow screen — the share and close buttons at `right-4` and `right-14` in `LetterModal` are the obvious pair.

- [ ] **Step 2: Write the findings**

Create `docs/superpowers/specs/2026-09-10-responsive-audit.md` with a header explaining what this is and is not:

```markdown
# Responsive audit — structural only

**Date:** 2026-09-10

Every component and route read for four classes of problem: widths that cannot
shrink, horizontal overflow risk, tap targets under 44px, and absolute
positioning that could collide on a narrow screen.

**This is not a responsive pass.** Nobody working on this project can see a
rendered page. These are suspects found by reading code; the verdict requires
someone opening the deployed site on a phone. Findings are listed so that
person knows where to look first.
```

Then a table of every finding: file, line, category, what was observed, and
whether it looks like a real risk or is fine as written. Include the items that
came back CLEAN too — a reader needs to know the URL rows were checked and
found to have `break-all`, not merely that they are absent from a list of
problems.

If a finding is severe enough that it would obviously break at 375px, say so
plainly at the top. Do not fix it — this task changes no styling.
